# PRAXIS-VirtualCell v0.9→v1.3 升级主路线图

> **性质**:这是一份**主路线图(master roadmap)**,不是可直接执行的 bite-sized 计划。它把新架构逐项落到 v0.8 真实代码上,给出 Phase 依赖顺序、版本里程碑、红线与决策。每个 Phase 的**可执行详细计划**单独成文(见 §9 索引),第一份 `2026-07-04-phase0-1-module-core.md` 已随本路线图交付。
>
> **一句话定位(不变)**:PRAXIS-VirtualCell 是一个**由 PRAXIS 智能体控制预测模型的多物种虚拟细胞系统**。PRAXIS 是操作系统,模型是插件,LLM 是编排员,治理层是裁判,主动学习是进化机制。

---

## 0. 本路线图解决的核心问题

用户给的新版计划非常完整(八模块 / 三支柱 / LLM 编排 / model zoo / 主动学习 / 五版本里程碑),但它是**架构规格**,里面大量引用"现有系统"。本路线图做三件规格文档没做的事:

1. **核实"现有系统"** —— 把新架构每一块**逐项对齐 v0.8 真实代码**,标清 🟢100%复用 / 🟡扩展现有 / 🔴净新增,避免"重复造轮子"或"以为要重写其实已有"。
2. **校正规格里的事实偏差** —— 几处会误导执行的地方(测试基线口径、GEARS 真伪、species profile 落位、目录命名冲突),在 §3 集中列出。
3. **定序与拆分** —— 把 9 个 Phase 按真实依赖排成可执行序列,每个 Phase 产出**能独立跑通、能测试**的软件切片(遵循 superpowers writing-plans 的"多子系统必须拆分成独立计划"原则)。

## 3. 对用户原规格的**事实校正**(执行前必读)

这几处若照规格字面执行会走弯路,已核实真相:

### 3.1 测试基线口径:是 277(内核)不是 1602(整仓)
- 规格说"现有测试 277 passed / 25 skipped"。核实:`pytest praxis_virtualcell/tests` = **277 passed / 25 skipped / 0 failed**(生物计算内核)。
- 但整仓 `pytest`(含根 `tests/` 186 文件)会 collect **~1602**,其中 **~1398 是继承自 PRAXIS-2 的 Web/Auth/Admin/Brains 框架测试**,与虚拟细胞无关(BASELINE.md 记录了其中 14 个 pre-existing 失败)。
- **红线:升级的所有测试目标(450+ passed)以 `praxis_virtualcell/tests` 为口径,277→450+。不要去动那 1398 个继承测试。** Phase 0 冻结的基线也是这 277。
- **决策(用户拍板 2026-07-04):这 ~1398 个继承自 PRAXIS-2 的 Web/Auth/Admin/Brains 框架测试永不纳入本项目维护范围——不修、不迁移、不计入 CI 绿勾口径、不计入 450+ 目标。它们是 bootstrap 时随 PRAXIS-2 代码一起复制进来的历史包裹(见 BASELINE.md),与虚拟细胞科学核心无关。升级全程只在 `praxis_virtualcell/tests` 内工作。**

### 3.2 GEARS/scGPT:在 .53 上真装真跑,但没进"离线优先可分发路径"
- **远端 .53 状态(2026-07-04 SSH 实测)**:GEARS 在 `virtualcell` env(torch 2.6+cu124)、scGPT 在 `vc-scgpt` env(torch 2.3+cu121)均已安装、GPU 可跑;donor 代码 `/home/zkyd/data1/mzy/Virtual cell/coordinator/`、scGPT 权重 `/home/zkyd/data1/mzy/scgpt_ckpt/norman_2019/pretrained_backbone.pt`(206MB)都在。scGPT 甚至已接到 `MLPredictorAgent`(`build_predictor_from_ckpt` 重建 backbone + head,`predict_tensor == donor predict` 逐元素等价,见 finding_w4c_scgpt.md)。
- **Mac 本地状态**:无 torch/GPU/donor 源码/数据/ckpt → 只有 `predictors/mock_gears.py`(每基因常数 0.4)在跑。`benchmarks/gears_*.py`、`scgpt_train_eval.py` 依赖硬编码 `/home/zkyd/...` + torch,本地 skip。
- "ΔPearson 0.7039(GEARS same-split)/ 0.7020(Coordinator)/ 0.4407(scGPT frozen)"都是 **.53 上真跑的锚点数字**,可信。
- **精确结论**:模型**能力在 .53 上是真的**;缺的不是"能不能跑",而是"有没有进项目的**离线优先可分发路径**"——即被 ModelBroker 声明、版本锁定、缺 torch/GPU/ckpt 时 fail-closed 优雅降级、带 provenance,让装了 wheel 的人也能在 registry 里看到它、按声明调用。
- **含义:Phase 6 = 把 .53 上这套"远端脚本 + 硬编码路径 + 200MB ckpt"产品化成 ModelBroker 插件**(ckpt/数据挪出硬编码路径 → registry 声明;GPU/torch 作为 optional extra,缺则 fail-closed;补 scope/provenance)。不是从零训模型,是把已有远端能力收编进治理框架。

### 3.3 species_profiles 落位:别新建平行目录,建在现有 brains 体系上
- 规格 §5 建议新目录 `praxis_virtualcell/species_profiles/{species}.yaml`。但物种规则**已经**在 `praxis_virtualcell/brains/virtualcell/{species}/*.yaml`(model_applicability/object_vocabulary/ortholog_rules/negative_transfer/abstain_rules),`SpeciesBrainAgent` 运行时读它。
- **决策(见 §6-D):新增的是 `brains/virtualcell/{species}/module_support.yaml`(8 模块支持度矩阵 + 可用模型 + AL 策略),它 references 现有规则文件而不复制。** 单一真相源:适用性/词汇/治理权威留在现有 brain 规则,module_support 只加"模块维度"的视图。避免双真相源。
- 顶层还有个 `brains/virtualcell/`(人读的 prompt/skill/memory)——那是另一套,别混。

### 3.4 "16 case" = golden 路由代表案例,不是 16 个独立文件
- 规格多处说"16 case = 5 应用 × 4 物种"。核实:这对应 `golden_cases/routing_representative.yaml`(12)+ `routing_safety.yaml`(6)= 18,runner 断言 ≥16。另外还有 13 个 `test_*_case.py` 深度模块(77 测试,真跑 GEM/LINCS)+ 14 negative。三层不是一回事,Phase 3 扩到 60 golden 时以 YAML 那套为主。

### 3.5 predictor 的 ModelWrapper 五方法:已有三个,补两个
- 规格 §4.1 要 `predict/validate_input/estimate_uncertainty/return_provenance/declare_scope/fail_closed`。核实 `predictors/base.py`:`assess_applicability`(≈declare_scope+validate_input)、`run_prediction`(≈predict)、`handle` 异常捕获(≈fail_closed)、`PredictorResultMessage.provenance`(≈return_provenance)已有;**只差显式 `declare_scope()` 和 `estimate_uncertainty()`**。Phase 2 补这两个即成统一 wrapper。

## 4. 管线插点(新 agent 如何进 message bus)

现有 `run_workflow`(`core/runtime.py:46`)是线性固定管线。新架构**在两处插节点**,其余不动:

```
现有:  client → InputInterpreter → BioObjectNormalizer → SpeciesBrain → ModelApplicability
                                                              │
              ┌───────────────────────────────────────────────┘
              ▼
        [插点 A] SpeciesContextAgent  ← 判物种可用模块/弱支持/不支持(读 module_support.yaml)
              ▼
        [插点 B] ModuleRouterAgent    ← 定 primary + secondary modules → 生成 ModulePlan
              ▼               (LLM_ORCHESTRATED 模式下:LLMModulePlanner 先出建议,经 safety_contract
              ▼                过滤成合法 module 集,再转 AgentMessage;OFFLINE 用确定性 module 规则)
        ModuleAgent×N          ← 每个选中模块 agent 调本模块的 predictor/engine(内部仍走现有 route+predictor fan-out)
              ▼
        EnsembleCoordinator → Reliability → [插点 C] EvidenceLevelAgent(E0–E5)→ Critic(+cross-module)
              ▼
        Provenance → [插点 D] ActiveLearningAgent(产 learning_queue)→ Report(+新段落)
```

**铁律(§7 展开)**:LLM 可以在插点 B 出 module plan,但 plan **必须转成 `AgentMessage` 才能执行**,且经 `assert_llm_boundaries` + safety_contract 三重检查。OFFLINE 模式插点 B 走确定性规则,零 LLM,与现在等价。

## 6. 关键架构决策(已拍板,写进各 Phase 计划)

- **A. 模块是逻辑视图,不是新引擎。** M1–M8 的 ModuleAgent 内部调的是现有 8 个 engine / predictor。M4(细胞质代谢)= gem_fba;M3(能量)= gem_fba + pathway_scoring;M2(基因枢纽)= donor_predictor + (未来)GEARS;M7(应激)= state_scoring + drug_signature。**不为每个模块造新模型**。空白模块走规则/abstain。
- **B. 证据等级是治理层之上的薄映射,不重写治理。** `evidence_level.py` 读现有 reliability/OOD/artifact 信号,映射到 E0–E5,再决定 verdict。E2=匹配扰动数据 in-domain→accept,与现有 disposition 对齐。
- **C. LLM 编排复用"只能从候选选"约束。** 现有 `LLMRouter`(`agents_llm/llm_router.py:37`)已经把 LLM 输出过滤成 `[a for a in ... if a in candidates]`。module_planner 复刻此模式:LLM 出 module 集 → 过滤成 support matrix 内的合法模块 → 转 AgentMessage。
- **D. species profile 建在 brains 体系内**(见 §3.3),新增 `module_support.yaml`,不建平行目录。
- **E. bacteria 术语映射硬约束。** M3 在 bacteria 前端显示 "Energy metabolism / redox",内部映射 M3;M8 "细菌自噬" → `unsupported/caution/biological_mismatch`(复用现有 abstain_rules 机制)。这些是 Phase 1 species-specific 测试要钉死的(bacteria 不套自噬、yeast 不套组织 niche)。
- **F. 目录落位**:`biological_modules/`、`model_zoo/`、`llm_orchestration/`、`active_learning/`、`data_pillars/` 作为 `praxis_virtualcell/` 下新子包;`governance/` 扩(加 evidence_level 等);`species_profiles/` **不建**,改用 §3.3 方案。

## 7. 红线(每个 Phase 的验收都要守)

治理和 LLM 边界是这个项目的**卖点本身**,升级过程一步都不能破:

1. **OFFLINE 零 LLM 不变**:默认 `mode=OFFLINE`、`llm_enabled=False`,核心 case/预测/治理零 token 可跑。CI/Linux 发行/审稿复现全走这条。
2. **`assert_llm_boundaries` 三 flag 恒 False**:LLM 绝不碰 prediction / hard-rule / learned-reliability 终决 / provenance / ledger。新增的 LLM_ORCHESTRATED 也守此线。
3. **LLM plan 必须转 AgentMessage**:LLM 不能直接执行,不能给 unsupported module 硬解释,不能把 downgrade 改 accept,不能新增无 provenance 的证据。
4. **unsafe-accept = 0 / 无静默 accept**:golden 与 negative 的两条 KPI 在每个 Phase 后都要绿。
5. **只读断言,不改逻辑迁就测试**:若新 route/module 输出与期望不符,是真 bug,停下报告,不改 golden 迁就(现有 golden-cases 计划已立此规矩)。
6. **模型缺失不能静默 accept**:公开模型没下到 / 自训模型没 provenance → fail-closed,不硬报。
