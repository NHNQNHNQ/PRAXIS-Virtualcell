## 一、项目概述

**PRAXIS-2** 是一个「领域智能体平台」：每个学科（蛋白设计、分子动力学、对接、酶工程……）配一个**带领域记忆的 AI 智能体**，用户在网页上用自然语言提问，智能体基于该学科的**案例库（cases）+ 规则库（rules）+ 可执行技能（skills）** 给出有据可查、可真实执行的分析。

与「套壳大模型」的本质区别：
- **领域大脑**：每个学科有从真实文献/实验提炼的案例和规则，智能体回答前先检索（BrainQuery），不凭空编造。
- **真执行**：智能体能通过 SkillExec / MCP 工具在 GPU 服务器上真跑分析软件（GROMACS、AlphaFold、对接、ADMET……），不是只描述步骤。
- **反幻觉闭环**：检索先行证据门 + stop_hook，智能体不能假称"跑过了"。

### 技术栈
| 层 | 技术 |
|---|---|
| 后端 | 纯 ASGI（无框架）+ Python 3.13，21 个模块，~2000 测试 |
| 前端 | React + Vite + TypeScript |
| 数据 | PostgreSQL（用户/会话/计费/MD作业）+ Redis（限流/配额） |
| 大脑 | 文件系统（cases/rules/skills 的 markdown + frontmatter） |
| 执行 | SSH → conda env 真跑 skill；MCP stdio server（gmx 等）；本地 BashTool（软沙盒+真隔离） |
| 部署 | `.53`（5×A100）主站 + `.40` 本科生入口，gunicorn + rsync 手动部署 |

## 二、系统架构全景

```
[浏览器] ──HTTPS──> [.53:8001 gunicorn (ASGI)]
   │                      │
   │                      ├─ auth (登录/会话/计费)
   │                      ├─ chat-stream (SSE 流式对话)
   │                      │     └─ Agent Kernel (RMCP 相位机)
   │                      │           ├─ BrainQuery   → 检索 brains/ cases/rules/skills
   │                      │           ├─ SkillExec    → SSH 到 .53 conda env 真跑 run.py
   │                      │           ├─ FileRead/WebFetch
   │                      │           ├─ BashTool     → 软沙盒/真隔离 shell
   │                      │           └─ mcp__<server>__<tool> → MCP stdio (echo/gmx)
   │                      ├─ /api/md/*  → MD 作业派发 (LocalJobRunner → A100)
   │                      ├─ /api/files/* → 文件上传 (PG + fs_store)
   │                      └─ /api/storage/* → 配额/轨迹
   │
   ├─ PostgreSQL (users/sessions/md_jobs/ledger)
   └─ Redis (限流/配额)

[.40:8080] 本科生入口（独立前端 dist + 反代到 .53 后端）
```

### 后端核心模块（praxis2/）
- `server/` — ASGI app、路由、chat-stream、SSE
- `agents/` — Agent Kernel、AgentTool、loader（学科选择）
- `core/rmcp.py` — RMCP 相位机（retrieve→plan→execute→seal）
- `tools/` — BrainQuery / SkillExec / FileRead / WebFetch / BashTool / RMCPWrite
- `mcp/` — MCP client（pool/config/tool_adapter）+ servers/（gmx_server）
- `md/` — MD 作业（sbatch 脚本生成 / local_runner / poll_worker / 增强采样）
- `auth/` `accounting/` `files/` `store/` `runtime/` — 基础设施

## 四、大脑文件格式规范

> 这是后续「补充 cases/skills」必须遵守的契约。所有大脑内容是带 YAML frontmatter 的 markdown。

### 标准学科目录结构（以 protein 为例）
```
brains/<学科>/
├── memory/
│   ├── cases/          # 案例库：<学科>-NNN-<slug>.md
│   └── rules/          # 规则库：NN-<slug>.md
├── skills/
│   └── workflows/
│       └── <skill_name>/
│           ├── SKILL.md    # 技能契约（必需）
│           └── run.py      # 真执行入口（可选，SkillExec 真跑用）
├── prompts/ 或 agents/ # runtime system prompt
└── (schemas/ indices/ scripts/ 等可选)
```

### case 文件格式（`memory/cases/<学科>-NNN-<slug>.md`）
```markdown
---
case_id: protein-013-bhardwaj2016-hyperstable-cyclic-peptide
design_task: cyclic_peptide_de_novo        # 任务类型（学科内枚举）
target_pdb: nan                            # 靶点 PDB（无则 nan）
target_uniprot: nan
fold_class: cyclic_macrocycle
tools: [Rosetta, GenKIC, NMR, X-ray]       # 用到的软件/方法
key_paper_doi: 10.1038/nature19791         # 来源文献 DOI（literature 类必填）
key_metrics:                               # 关键定量指标（可审计）
  designs_synthesized: "12 ..."
  Tm_designs: ">95 deg C"
status: validated                          # validated / proposed / ...
schema_version: 1
source: literature                         # literature / experiment / ...
extracted_at: 2026-05-01
tags: [cyclic-peptide, GenKIC, NMR-validated]
unverified_details:                        # 诚实标注未核实项（反幻觉关键）
  - "Exact PDB IDs: see supp; not enumerated"
---

# 标题（中文叙述）
正文：背景、方法、结论、可迁移经验……
```

### rule 文件格式（`memory/rules/NN-<slug>.md`）
```markdown
# NN 规则标题

## 核心规则
一句话铁律。

## 适用
- 场景 1
- 场景 2

## 为什么
- 原理 / 失败模式

（可加命令示例、注意事项小节）
```

### SKILL.md 格式（`skills/workflows/<name>/SKILL.md`）
```markdown
---
name: antibody_pipeline
description: 一句话能力描述
status: green                # green=可真跑 / 其他=未就绪
host_env: praxis-protein     # 真跑用的 conda env
deps: [anarci]               # 额外依赖
---

## 一句话原则
## 适用场景 / 不适用
## 环境检查（bash）
## 输入契约（JSON）
## 输出契约（JSON）
```

## 五、Roadmap

### Phase 1（下一步）：充实大脑 + 解锁软件 + 扩 MCP + 整理格式

目标：把「能跑的学科」从 MD 一个，扩展到多学科真执行；同时把大脑内容和格式整理干净。

#### 1.1 补充大脑分析例子（cases）和技能（skills）
- 每学科盘点 case 覆盖度，对高频任务补充**真实文献提炼**的 cases（严格遵守 §四 格式 + DOI + unverified_details）
- 为缺失的核心分析补 skills（SKILL.md 契约 + run.py 真执行入口）
- 优先级参考 GAP-E2E 现状（见 §六）：先补已有 env 能跑的学科

#### 1.2 在环境中下载/安装软件
GAP-E2E 已暴露一批 skill 因**缺依赖**跑不通（RED/ERROR），需在对应 conda env 补齐：
- 模型权重（esm 损坏、boltz 权重需联网）
- 配置文件（rfdiffusion Hydra config）
- 二进制（vina）、数据库（kraken DB、checkm2 DB）
- **前置阻塞**：部分需 `.53` 出站网络（egress）解锁才能下载——需 ops 配合
- 安装遵循 per-env `activate.d/` scoping（不污染全局 LD，见雷区）

#### 1.3 补充 MCP server
- 现有：`echo`（测试）、`gmx`（GROMACS 交互式）
- 计划新增：按学科把高频交互式工具包成 MCP server（如对接、结构预测、序列分析），让智能体像调 gmx 一样交互式调用
- 模式：参考 `praxis2/mcp/servers/gmx_server.py`（纯 `_impl` 函数 + FastMCP 绑定 + SAFE_ROOT 路径隔离）
- 注册：`praxis2.env` 的 `PRAXIS_MCP_SERVERS_JSON` 加条目；MCP 工具全局注入所有 chat agent 池

#### 1.4 整理大脑文件格式
- [ ] 清除 609 个 `._` AppleDouble 文件（`find brains -name '._*' -delete`，先确认无误伤）
- [ ] md 学科结构归一：`Naruto-main/` 内容上提到 `brains/md/memory/` + `brains/md/skills/`，与其他学科一致
- [ ] 重建 `brains/INDEX.md`：脚本自动统计真实 cases/rules/skills 数，列 14 学科
- [ ] case frontmatter schema 校验脚本：扫描缺字段的 case，补齐 design_task/source/status/schema_version
- [ ] 统一 skill `status` 字段语义（green 必须真能跑，与 GAP-E2E verdict 对齐）

### Phase 2（再下一步，先预备）：Docker 化 + 迁真服务器

目标：从「手动 conda + rsync + 手启 gunicorn」迁移到「容器化可复现部署」，上真正的生产服务器。

#### 2.1 容器化设计（预案）
- **后端镜像**：Python 3.13 + praxis2 + gunicorn/uvicorn，多阶段构建
- **前端**：Vite build 产物 → nginx 静态服务（或后端 static root）
- **大脑**：brains/ 作为 volume 挂载（~1GB，不进镜像，便于更新）
- **GPU 软件栈**：这是难点——14 学科 conda envs（GROMACS/AlphaFold/对接……）体积大、含 CUDA。
  - 方案 A：分层镜像，每学科一个 GPU 镜像（base CUDA + 该 env），按需调度
  - 方案 B：软件栈留宿主机/共享 volume，容器只跑后端 + SSH/MCP 到 GPU 节点（沿用当前 .53 模式，但容器化后端）
  - 推荐先做方案 B（改动小、风险低），方案 A 作为多节点扩展时再上
- **依赖服务**：PostgreSQL + Redis 用官方镜像，docker-compose 编排
- **配置**：现 `praxis2.env`（凭证）→ Docker secrets / env file，**绝不进镜像层**

#### 2.2 部署模式
- docker-compose（单机）起步：backend + frontend(nginx) + postgres + redis
- GPU 执行节点：容器化后端通过 SSH/MCP 连 GPU 节点 conda env（方案 B）
- 真服务器迁移清单：
  - [ ] 凭证轮换（git 历史含明文，见雷区）+ Docker secrets
  - [ ] 反代/TLS（nginx/caddy）+ 域名
  - [ ] gunicorn 改 systemd service 或容器托管（解决当前「手动 user session、HUP 不重读 env」雷区）
  - [ ] 数据迁移（PG dump/restore）+ 备份策略
  - [ ] 健康检查 + 日志聚合 + 监控

#### 2.3 当前部署的遗留问题（迁移时必须解决）
- gunicorn 是**用户 SSH session 手动启动**（非 systemd），HUP 只重载代码不重读 env → 容器化天然解决
- 凭证明文曾 push GitHub（已脱敏但历史残留）→ 迁移时必须轮换
- 软件环境靠 per-env `activate.d/` 打补丁（如 MD 的 LD 前置、plumed 的 LD_PRELOAD）→ 容器化需固化进镜像/启动脚本
