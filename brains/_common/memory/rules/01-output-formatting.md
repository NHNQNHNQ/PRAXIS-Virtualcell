# 输出呈现规范(_common,所有 agent 生效)

本规则约束**所有学科智能体**面向用户的最终回答的呈现格式。前端用
ReactMarkdown 渲染、比例字体(非等宽),故表格必须用标准 markdown 语法,
对比表必须给出可支撑决策的实用维度。

## 1. 表格一律用标准 markdown 语法,禁止手画 ASCII 竖线表格

**Why**:前端是比例字体(非等宽),用空格 + `|` 手动对齐画的"竖线表格"在
渲染后竖线参差不齐、完全错位,无法阅读;只有标准 markdown 表格会被
ReactMarkdown 渲染成真正的 HTML 表格,自动对齐。

**How to apply**:
- 任何需要表格的场景,**必须**用标准 markdown 表格语法:表头行 + 紧跟一行
  分隔符 `| --- | --- |`(每列一个 `---`),再是数据行。例:

  ```
  | 方法 | 优点 | 适用场景 |
  | --- | --- | --- |
  | Cellpose 3 | 泛化强、免训练 | 单层荧光细胞 |
  | Mesmer | 组织多重成像准 | CODEX/IMC 组织 |
  ```

- **禁止**用空格手动 padding 对齐列宽来"画"表格(等宽字体下看着齐、用户端
  全错位);禁止省略 `| --- |` 分隔行(省了就不是表格,会被当普通段落)。
- 单元格内换行/复杂内容用 `<br>` 或拆成多行短句,不要靠空格凑宽度。
- 仅 2-3 个并列项且每项一句话时,可用无序列表代替表格,更稳。

## 2. 对比表优先选实用决策维度,不要堆元信息

**Why**:用户看方法对比表是为了**做选择**。把列填成"年份 / 作者 / 出处"
这类元信息(metadata)对选型几乎没用;真正有用的是优缺点、适用条件、
代价权衡。

**How to apply**:
- 方法/工具对比表的列,**优先**选这些实用维度(按场景取 3-5 个):
  - **优点 / 缺点**(或"长处 / 短板")
  - **适用场景 / 适用条件**(什么数据、什么任务、什么规模下用它)
  - **不适用 / 失效边界**(什么情况下别用)
  - **计算成本 / 资源**(GPU 需求、运行时长、是否需训练)
  - **精度 / 性能基准**(有定量 benchmark 时给数值 + 出处)
  - **依赖 / 可得性**(开源/商业、是否需许可、是否在本平台可跑)
- **避免**把列设成纯元信息:年份、第一作者、期刊、DOI 单独成列。这些可作为
  "凭据"放在最后一列(如 `凭据 case` / `参考文献`),**但不能是对比的主维度**。
- 选型结论:对比表后必须给一句"在用户当前场景下推荐 X,因为 …",不要只甩表
  让用户自己猜。

## 边界(规则不适用)

- 代码块、命令行示例、纯文本日志:保持原样,不套表格。
- 用户明确要求等宽对齐 / ASCII art / 纯文本表格时,从其要求。
- 数据维度过多(> ~6 列)放不下时,改用分组小表或要点列表,不要硬塞一张宽表。
